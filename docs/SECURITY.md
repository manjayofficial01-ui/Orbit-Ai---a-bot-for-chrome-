# Security and privacy

## Data flow
Explicit message + retained conversation + attached text + custom instructions/memory → extension page → selected provider over HTTPS (or loopback HTTP) → streamed/JSON reply → plain DOM rendering → optional local history.

Image retention in a conversation is deliberately narrow: only the most recent screenshot is re-sent on later turns. Earlier image attachments are replaced by a text note telling the model the screenshot is no longer attached, which limits both how much screen content keeps leaving the machine and how much you are billed for it.

No analytics, Orbit server, shared API key, hidden content-script collection or externally connectable endpoint is included. A supervised model-driven page-action loop is included (Agent mode): it proposes snapshot/screenshot/click/fill/type/select/scroll/focus/hover/press/wait/extract/read-tab/goto/nav-history/done actions as fenced JSON, and the extension executes at most 3 actions per step, max 8 steps, only after your per-step confirm() gate. The approval dialog names the origin the actions will run on and that origin is refreshed whenever an action navigates the page; any navigation — a `read-tab` switch, `goto`, or `nav-history` — ends the step so that refs from the previous page cannot be reinterpreted against the newly loaded one. `goto` accepts only plain http(s) URLs without credentials, shows the full destination URL in the approval dialog, requests the destination site's access before navigating, and refuses to navigate if the grant is denied. `screenshot` captures the visible tab of the target window as a JPEG only after that same per-step gate, only when the target tab is the visible tab of its window (otherwise it is refused), and the image is sent to your provider as vision input; at most two captures (~3 MB) attach per step and earlier steps' images are pruned. `press` is limited to Tab, Escape, Enter and the four arrow keys — Enter is surfaced in the approval dialog with an explicit "can submit the focused form" warning, and nothing auto-submits: no action runs without that step's approval. A supervised research loop is also included (Reach research): through a restricted native-messaging bridge it runs only status/search/read operations of the separately installed Agent Reach CLI, at most four proposed calls per run, each requiring approval before any network request, with results wrapped as untrusted data before being shown to the model.

## Native bridge (Reach research)
The nativeMessaging permission powers one fixed host name, ai.orbit.agent_reach, whose manifest the user installs manually and which allows only this exact extension ID. The bridge accepts exactly three operations (status, search, read), validates every field, and forwards a fixed argv shape to the agent-reach executable — never a shell, never caller-chosen arguments. Output is size-capped and stripped to a bounded schema; raw upstream payloads and credentials never cross the bridge. The bridge stores only the agent-reach executable path. Orbit never sends provider keys, cookies or passwords to Agent Reach, and cannot install, update, log in to, or configure Agent Reach.

## Permissions
- sidePanel: native workspace.
- storage: profiles, local history, locally persisted keys and transient selection drafts.
- activeTab + scripting: user-invoked page/selection text extraction plus supervised Agent-mode snapshot and action execution, each step gated by confirm().
- contextMenus: selected-text draft handoff, not automatic submission.
- tabs: reads the title and URL of every open tab. This is metadata, not page content, and it is what lets the all-tabs digest and Agent-mode `read-tab` show you which tabs exist. Page *text* of a tab is still read only after the site permission for that origin is granted. Tab titles can themselves be sensitive (search terms, document names, mail subjects); the digest and the agent observation include them and are labelled untrusted.
- nativeMessaging: restricted Agent Reach bridge — status/search/read only, per-call approval, fixed argv, bounded output, extension-ID-pinned host.
- optional HTTPS/loopback hosts: user-approved provider and page fetch access.
- optional `<all_urls>` host access exists for one purpose: Chrome's capture API (`captureVisibleTab`) ignores per-origin grants — it accepts only a fresh activeTab gesture (clicking the Orbit toolbar icon on a tab) or all-sites access. When a capture is refused, Orbit requests `<all_urls>` once, contextually; approving it lets screenshots (the Screenshot/Analyze buttons and the agent's screenshot tool) work everywhere, and it can be revoked at any time from Chrome's extension site permissions. It is never requested at install, never required, and page *text* reading keeps using per-origin grants.
- optional hosts also include all of `http://*/*` and `http://localhost/*` / `http://127.0.0.1/*`. Only the specific origin a page action targets is ever requested, but a plain-HTTP grant means that site's content travels unencrypted and is readable by any extension with host permissions. Prefer HTTPS pages.

A provider host permission is not limited to the entered API path. Review the domain before approving. Localhost origin checks and server authentication remain the local server's responsibility.

Settings → **Test connection** sends one real, small generation request to whatever endpoint and model are configured (a fixed one-word prompt, output capped at 64 tokens unless you set a lower cap) and may bill accordingly; it is never sent automatically, and the background model-list refresh on endpoint change is a plain `GET /models` with no generation. **Fetch models** only reads the list. Neither action adds hosted provider tools to the request.

## Reading text out of images

"Read text (OCR)" and attaching an image file use **the provider you configured**: the image is sent to that endpoint as an ordinary multimodal request and the model's transcription is returned as editable text. That means the image's contents — which may include passwords, account data or personal information visible on screen — leave your machine exactly as they would for any other attached image, and the request is billed by your provider. A dedicated transcription instruction tells the model to output only visible text and to treat any instructions embedded in the image as content rather than commands, but that is a prompt, not enforcement: a rendered page can still attempt injection through its pixels.

If the model path is unavailable (no vision support, no host grant, empty reply), Orbit falls back to the bundled on-device engine and **labels which one produced the text**, so you are never told "local" about something that left the machine. The fallback itself makes no network call.

## Vendored OCR engine and the CSP exception

Local image text extraction uses a vendored build of Tesseract.js (engine, worker, WebAssembly core and one English language model — about 6.8 MB) copied from `vendor/tesseract/` into `dist/vendor/` at build time. It adds **no permission** and **no network access**: every path is a `chrome-extension://` URL, the module contains no `fetch` call, and a test asserts both. `vendor/VENDOR.md` records the upstream source, version and sha256 of each file, and `tests/ocr-static.test.mjs` recomputes those hashes so a changed binary fails the suite rather than shipping quietly.

The one thing it does cost is CSP: running WebAssembly requires `'wasm-unsafe-eval'` in `script-src`, so the policy is now `script-src 'self' 'wasm-unsafe-eval'`. That permits executing self-hosted WebAssembly — it does not allow remote scripts, remote wasm, `unsafe-inline` or `unsafe-eval` of JS, and a test pins the rest of the policy so the relaxation cannot creep further. Practical consequence: anyone who can write into your unpacked extension folder can already run code as that extension; the wasm allowance does not add a new attacker, but it does mean the `vendor/` files must be reviewed as carefully as source. Only the SIMD core is shipped, so on a CPU without SIMD OCR reports that it is unavailable — it never falls back to sending your image somewhere else.

OCR output is untrusted content like any other reference: it is labelled as machine-read text, shown in the editable preview, and only reaches your provider if you send it. Accuracy is not guaranteed — measured on a real capture it read large body text at ~90% engine confidence but garbled smaller lines, so review what it extracts.

## Key handling
Keys are bound to normalized full base URLs and persisted in chrome.storage.local. They are not written to chat history or exports. Editing the endpoint shows the saved key for that endpoint if one exists. Fetch omits cookies/referrers and rejects redirects. HTTP errors display only status/generic advice rather than an arbitrary provider body that might echo secrets. Requests are not automatically retried.

chrome.storage.local persists across browser restarts. See https://developer.chrome.com/docs/extensions/reference/api/storage . It is not an encrypted vault and cannot protect against a compromised browser, extension context or operating system. Transient selection drafts still use chrome.storage.session.

OpenAI warns against exposing developer application keys in client-side code: https://developers.openai.com/api/reference/overview/ . This package is a personal BYOK utility. Do not distribute your own API key; use an authenticated backend for a managed multi-user service.

## Rendering and prompt injection
Text/HTML from models and pages is inserted via textContent, not innerHTML. No remote Markdown parser, eval, generated scripts, media/forms or tracking images are used. Provider citation links are restricted to HTTP(S), opened with noopener noreferrer. This does not prevent phishing at an HTTPS destination.

Page/file reference previews support manual review and bounded size. Page extraction skips common form/editable/navigation/hidden elements but is not a sensitive-data detector. The all-tabs digest applies equivalent hidden-text filtering, using an ancestor style climb instead of a layout check (a background tab may never have been painted, so layout-dependent visibility tests can silently return nothing there); like the other extractors it also skips `[contenteditable]` regions. The digest is previewed as one combined blob before you attach it, so review it — it can gather material from sites you did not mean to include. The direct URL fetch is HTTPS-only (loopback HTTP excepted), rejects URLs with embedded credentials, refuses redirects, sends no cookies or referrer, decodes using the declared charset, caps the download at 2 MB while reading, and parses HTML for text only — no scripts execute. Malicious reference instructions can influence answers. Delimiters (<untrusted_page>/<untrusted_reference>) are not enforcement. Agent mode adds client action tools (snapshot/screenshot/click/fill/type/select/scroll/focus/hover/press/wait/extract/read-tab/goto/nav-history) with token-bound refs, URL-change guards, sensitive-field blocks, and a per-step confirm() gate; no tool submits a form by itself, though a submit-capable element can still be activated — by click, or by an approved Enter whose dialog carries the submit warning — if you approve the step that targets it. The origin named in that approval dialog is re-read from Chrome after every step, including when a post-action snapshot fails. Provider-hosted search can still send queries influenced by attached text.

Provider-hosted tools are a separate exposure and all three are opt-in, Responses-format only, and refused on hosts that do not serve them: web search (official OpenAI or xAI), X search (xAI only — sends your query and any attached image to xAI, with image understanding enabled), and code interpreter (xAI only — executes model-written code on xAI's servers, never on your machine, but it is real remote computation that can be billed without a per-call prompt). None is enabled implicitly: Agent mode and Reach research strip all hosted tools from the request before it is built, so a supervised run cannot start incurring provider charges behind the approval dialog.

## Retention and deletion
Chat text, attachments, profile instructions and memory notes are not encrypted by Orbit. The active profile controls whether chat history is persisted. Memory notes remain in settings until deleted. Local deletion cannot delete provider records. Responses uses store:false, but that is not a universal zero-retention guarantee.

## Concurrency and resource boundaries
Single UI writer via Web Locks; explicit tab handoff. Five-minute generation timeout (ten-minute research cap); bounded request/reference/output sizes; save checkpoints; failed/interrupted output labeled and excluded from assistant replay. No resumable job backend. App save budget 8 MB and 100 chats. Model listing has a post-read size check, not a hostile-server streaming memory bound. SSE size guard applies to an individual unbroken buffered line, not a total network download quota. A malicious provider is not isolated by these limits.

## Release requirements
Not security-certified or store-reviewed. Complete native browser QA, real-provider tests, independent security/accessibility review and privacy-policy/store requirements before public distribution. Distribute source you trust, never add shared keys or remote executable code.


## Screenshots and smart context
Smart context (default on, Settings → Context) attaches a fresh, privacy-filtered text snapshot of the active tab to **every** message automatically — not only page-referential prompts — unless the message already carries a manually attached reference or the toggle is off. Orbit never reads its own workspace tab. Each site still requires its access grant, requested the first time you send while on that site; if you decline, the message is sent without page context and the model is instructed to say the page could not be read and ask you to grant access and resend — it must not pretend it read anything. Screenshot capture is explicit, limited to the active visible tab, and previewed before attachment; because Chrome's capture API ignores per-origin grants, a refused capture triggers a one-time optional `<all_urls>` request (see Permissions) and a single retry — declining it yields clear guidance, never a silent failure. The preview dialog's Analyze now action sends that same reviewed capture (it never takes a new one) with a fixed analysis prompt through the normal message path. Both features request site access at runtime. The Agent-mode `screenshot` tool is a separate capture path: it is gated by the per-step confirm() dialog like every action, is refused when the target tab is not the visible tab of its window, and its output goes to your provider as image data, not to any Orbit server. Page text, URLs, and screenshots can contain sensitive or malicious content and are wrapped/treated as untrusted provider input. Automatic context means page text ships with most messages — turn the toggle off, or use a conversation without it, when that is not what you want. Provider/model vision compatibility is not guaranteed: a text-only model will return a provider error, which the run reports honestly.
